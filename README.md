# Takebase

Takebase is a Cloudflare-native, PocketBase-inspired backend framework: TypeScript and Hono on Workers, with an independent D1 database per tenant, Firebase Auth for identity and Firebase RTDB for change notifications.

> Early development. Nothing here is published or production-ready yet.

## Layout

| Path | Contents |
| --- | --- |
| `packages/core` | `@takebase/core`, the server framework: request store, collections (rules, validation, list queries, hooks) |
| `packages/contracts` | `@takebase/contracts`, HTTP error/list envelopes, collection operations and tenant types; no dependencies |
| `packages/sdk` | `@takebase/sdk`, the client SDK: tenant discovery and selection, collection CRUD and realtime `subscribe`; depends only on contracts |
| `packages/adapter-firebase` | `@takebase/adapter-firebase`, the Firebase RTDB realtime adapter for Workers and its browser connector (`/client`) |
| `packages/cli` | `@takebase/cli`, the `takebase` command and its bundled local starter template |
| `examples/workers/global` | Example global Worker: tenant discovery, its own D1 database |
| `examples/workers/tenant` | Example tenant Worker: one deployment per tenant, each with its own D1 database (`tenant-a`, `tenant-b` locally) |
| `examples/sveltekit` | The local milestone app: sign-in, tenant selection and a realtime policies list (see its README) |
| `migrations/global`, `migrations/tenant` | D1 migrations generated by drizzle-kit and applied by Wrangler (global has none yet) |
| `tests/architecture`, `tests/contracts`, `tests/cli` | Package boundary, public API and CLI checks |
| `tests/fixtures`, `tests/e2e` | The local two-tenant stack (`pnpm dev:stack`) and its browser tests (`pnpm test:e2e`) |
| `firebase/`, `firebase.json` | Local Firebase Auth/RTDB emulators (see `firebase/README.md`) |

## Development

Requires Node.js 24 and pnpm (version pinned in `package.json`).

```sh
pnpm install
pnpm lint        # Biome
pnpm typecheck   # TypeScript and svelte-check in every package
pnpm test        # Workers tests in the Workers runtime, plus architecture, contract and CLI checks
pnpm build       # core declarations, Worker bundles (wrangler --dry-run) and the SvelteKit build
pnpm test:firebase   # Firebase emulator checks; needs the Firebase CLI and Java
pnpm test:realtime   # realtime adapter and connector against the emulators; same needs
```

Run a Worker locally from its directory with `pnpm dev`, for example `pnpm --filter @takebase/example-tenant dev --env tenant-a`. Pass Wrangler flags directly, with no `--` in between: pnpm forwards a literal `--` and Wrangler then ignores the flags after it, so the Worker silently starts with the default `local` environment. All D1 databases are local; no Cloudflare account is needed for development or tests.

## Local milestone

`pnpm dev:stack` runs the whole product locally: the Firebase Auth and RTDB emulators, the global Worker, two tenant Workers (`tenant-a`, `tenant-b`) and the SvelteKit app at `http://localhost:5173`, with seeded users and fresh tenant databases on every start. It is `takebase dev --fresh --seed 'node tests/fixtures/seed.ts'`: `takebase dev` provisions every tenant declared in `takebase.jsonc` (see [Tenants](#tenants)) and the fixture seed adds the users and their memberships. Emulators and local D1 only; no Firebase or Cloudflare account is used. The [SvelteKit example README](examples/sveltekit/README.md) lists the users and what to try. Stop it with `pnpm dev:stack:stop` (`takebase dev --stop`) from another terminal: Ctrl-C can leave the emulators or a `wrangler`/`workerd` holding a port, and the stop command ends every process listening on the stack's ports.

`pnpm test:e2e` starts a fresh stack and runs the browser tests in Chromium (install it once with `pnpm exec playwright install chromium`). They cover creating a policy and seeing it arrive by realtime, switching tenants, reconnecting, signing out and a removed member being signed out.

Browser origins are allowed per Worker with the `CORS_ORIGINS` variable (comma-separated exact origins; unset means no cross-origin access). The stack sets it for the local app only.

## Staging

An approved staging copy of the milestone runs on real services (SEGU-218):

- **Firebase:** project `takebase-eb6e3`, with one Realtime Database per tenant (`takebase-staging-tenant-a`, `-b`).
- **Cloudflare:** Workers on workers.dev and one D1 database per Worker, all named `takebase-staging-*` in a shared account. Never create or touch anything outside that prefix.

| What | URL |
| --- | --- |
| App | `https://takebase-staging-app.info8841.workers.dev` |
| Global Worker | `https://takebase-staging-global.info8841.workers.dev` |
| Tenant Workers | `https://takebase-staging-tenant-a.info8841.workers.dev`, `…-tenant-b…` |

You need:
- a Firebase CLI login with access to the project;
- a Wrangler login for the account;
- the untracked `ops/.staging.env` (mode 600). It holds the web app config and the generated staging passwords; the scripts write it and never print it. Secrets reach the Workers only through `--secrets-file` uploads.

Run each step from the repository root and check it before going on:

```sh
# Firebase (only after console setup: Email/Password sign-in, default RTDB, Blaze)
pnpm staging:firebase:setup   # users and rendered tenant rules (safe to rerun)
pnpm staging:firebase:rules   # deploys those rules
pnpm staging:firebase:check   # rules, dispatchers, grants, revocation, tenant isolation

pnpm staging:local:check      # the real Workers via wrangler dev, against real Firebase

# Cloudflare (the CLI, see "Dev, build and deploy")
pnpm staging:deploy:plan      # takebase deploy --env staging --plan: read-only
pnpm staging:deploy           # takebase deploy --env staging --confirm staging: migrations, Workers, app
pnpm staging:check            # takebase doctor --env staging, then health, membership RPC, app page
pnpm staging:health           # takebase health --env staging: every Worker live and ready
pnpm staging:logs             # takebase logs tenant-a --env staging --for 60: live, redacted
pnpm staging:seed             # tenants and memberships; clears the tenants' RTDB signals
pnpm staging:journey          # identity → tenant → create → signal → refetch, negative auth, isolation
pnpm staging:journey:wire     # S-5-3-01: a dead notification inspected, refused to others, retried, refetched
pnpm staging:e2e              # the browser journey against the deployed app
```

`staging:local:check` and deployed staging share the tenants' Realtime Databases, and the local check restarts its revision counters on every run. Run `pnpm staging:seed` after a local check, before the deployed journey. Otherwise stale signals hide new changes, because the adapter ignores any revision that is not newer than the stored one.

New staging tenants are provisioned with `takebase tenant create <id> --name <name> --env staging`. SEGU-219 proved this with `tenant-c`: it was provisioned, disabled (revocation confirmed) and its registration deleted. Its resources (`takebase-staging-tenant-c` Worker, D1, Realtime Database and dispatcher user) were left up on purpose and are no longer declared in `takebase.jsonc` or `wrangler.jsonc`.

Teardown is manual and is never run by these scripts. Pin every Wrangler call to the account, because the account is shared: prefix it with `CLOUDFLARE_ACCOUNT_ID=<value from ops/.staging.env>`.
- Cloudflare: `wrangler delete <name>` for `takebase-staging-global`, `-app`, `-tenant-a`, `-tenant-b` and `-tenant-c`, then `wrangler d1 delete <name>` for `takebase-staging-global`, `-tenant-a`, `-tenant-b` and `-tenant-c`.
- Firebase: `firebase database:instances:delete <name> --project takebase-eb6e3` for the three `takebase-staging-tenant-*` databases, then delete the staging users (including the dispatchers) in the Firebase console.

## CLI

Run the CLI from the repository with `node packages/cli/src/bin.ts <command>` (Node.js 24 runs the TypeScript source directly). `takebase --help` lists the supported and planned commands.

```sh
node packages/cli/src/bin.ts create my-app   # new starter in ./my-app
node packages/cli/src/bin.ts init            # starter in the current directory
```

`init` and `create` copy a local Hono + D1 Worker starter. They refuse a non-empty directory unless `--force` is given, never follow symbolic links, and copy no credentials.

| Command group | Capabilities | Status |
| --- | --- | --- |
| `init` / `create` | Generate a project starter | Implemented |
| `dev` / `build` / `deploy` | Run locally, bundle, deploy a remote environment | Implemented |
| `doctor` | Validate environment and configuration | Implemented (read-only) |
| `user` | Create, list, disable, enable, delete users; revoke sessions | Implemented (operator) |
| `tenant` | Create, list, provision, disable, delete tenants | Implemented |
| `tenant user` | Add/remove members and assign roles | Implemented (operator) |
| `role` / `invite` | Manage roles and invitations | Implemented (operator) |

| `wire` | Inspect notification delivery, test it, retry dead events | Implemented (operator) |

### Environments and doctor

`takebase.jsonc` at the repository root names the deployment environments (`local` and the approved `staging`), the Worker directories, and for each tenant the Wrangler environment holding its bindings. It holds nothing secret. A remote environment also names the prefix every resource name must start with (`takebase-staging-`) and its untracked secrets file (`ops/.staging.env`, mode 600). That file also holds `CLOUDFLARE_ACCOUNT_ID`, which pins every remote Wrangler call to one account.

```sh
node packages/cli/src/bin.ts doctor               # local: tools, configuration, local D1
node packages/cli/src/bin.ts doctor --env staging # adds secrets (presence only), identity, resources, remote D1
```

`doctor` only reads. It prints `ok`, `warn` or `FAIL` per check and exits 1 when any check fails. Secret values are never printed.

### Tenants

```sh
# locally: inside the emulators, e.g. firebase emulators:exec --only auth,database --project demo-takebase '<command>'
# remotely: add --env staging
node packages/cli/src/bin.ts tenant create tenant-c --name "Tenant C" --port 8790   # declare, then provision
node packages/cli/src/bin.ts tenant provision tenant-c --plan                       # detect only; changes nothing
node packages/cli/src/bin.ts tenant provision tenant-c                              # resume or check
node packages/cli/src/bin.ts tenant list                                            # registration and pending revocations
```

`tenant create` adds the tenant to `takebase.jsonc` and then provisions it. Provisioning detects each resource before it creates it, in this order:

1. Realtime Database
2. dispatcher user
3. rules
4. D1 database
5. the tenant's Wrangler environment in the tenant `wrangler.jsonc`
6. tenant migrations
7. stale realtime signals: a revision above the tenant D1's newest outbox revision is cleared
8. deploy (remote only)
9. registration in global D1

A rerun after any failure resumes where it stopped and never creates anything twice. An existing Wrangler environment or registration that differs from what provisioning expects stops it instead of being overwritten. The tenant is registered last, so a half-provisioned tenant is never discovered. Provision never enables a disabled tenant.

Remotely, provisioning creates a `<namePrefix><tenant>` Realtime Database instance, signs the dispatcher up through Identity Toolkit (generating its password into the secrets file when there is none yet), deploys the rules to that one instance with your Firebase CLI login, creates the D1 database, deploys the Worker with its secrets from a temporary mode-600 file and waits for its `/health`. Any name outside the prefix stops it before a call is made.

```sh
node packages/cli/src/bin.ts tenant disable tenant-c                     # deny now, then revoke realtime
node packages/cli/src/bin.ts tenant delete tenant-c --confirm tenant-c   # registration only
```

`tenant disable` changes the status in one statement. Membership is read on every request, so the API refuses the tenant's members at once, and the same statement records a tenant-wide realtime revocation. The command then calls the tenant Worker's `/api/realtime/reconcile` (with backoff) until global D1 shows the revocation confirmed. If the Worker cannot be reached it exits 1 with the revocation still pending; run it again. `tenant delete` refuses unless the tenant is disabled, its revocation is confirmed and `--confirm <id>` repeats the id. It removes only the registration (memberships go with it) and prints the commands that would remove the tenant's resources, which it never runs itself.

### Users, members, roles and invitations

```sh
node packages/cli/src/bin.ts user create --email carol@example.test --password-file carol.pw   # password only in carol.pw (mode 600)
node packages/cli/src/bin.ts role create tenant-a support
node packages/cli/src/bin.ts tenant user add tenant-a <uid> --role support
node packages/cli/src/bin.ts tenant user remove tenant-a <uid>          # ends the membership, revokes realtime
node packages/cli/src/bin.ts user disable <uid>                         # refused everywhere, realtime revoked
node packages/cli/src/bin.ts user revoke-sessions <uid>                 # tokens from earlier sign-ins refused
node packages/cli/src/bin.ts invite create tenant-a --role support      # prints a single-use token once
```

These commands are the operator's: they write global D1 with your Cloudflare login (add `--env staging` for the approved staging), and each change is recorded in `audit_events`.
- **Rules:** global D1's triggers enforce them, so a refused change leaves nothing behind. A role must be declared for the tenant before anyone can hold it, and `admin` is built in. A tenant never loses its last admin.
- **Users are refused by Takebase itself.** A disabled or deleted user, or a token from a sign-in before `revoke-sessions`, gets 401 everywhere. The SDK then signs them out. The Firebase account is never disabled or deleted.
- **Realtime:** a user who loses access also loses realtime. The command calls each tenant Worker's reconcile until the revocation is confirmed; if a Worker cannot be reached, it exits 1 and you run it again.

### Health, logs and notification repair

```sh
pnpm smoke:diagnostics                                           # local acceptance: checks, health, the S-5-3-01 journey
node packages/cli/src/bin.ts health [--env staging]              # /health and /health/ready of every Worker, then the app
node packages/cli/src/bin.ts wire status tenant-a [--env staging] # outbox counts, dead events, revocations owed
node packages/cli/src/bin.ts wire test tenant-a                  # deliver what is pending once
node packages/cli/src/bin.ts wire retry tenant-a --dead          # or --event <id>…: revive dead events, deliver with retries
pnpm staging:logs                                                # live tenant-a logs on staging for 60 s
```

- **Health:** `/health` is liveness. `/health/ready` reports each dependency as `ok`, `error` or `unconfigured`, never why (HTTP 503 on error); the reason goes to the Worker's log.
- **Logs:** every Worker log line is one redacted JSON event carrying the request's `x-request-id` (a well-formed client id, else `cf-ray`, else a UUID). Tokens, passwords, secrets, sensitive URL parameters and email addresses are masked, and errors keep only name and message. `takebase logs` streams `wrangler tail` and prints method, path without its query, status and request id per request, also masking the secrets file's values. Nothing is stored; history stays in Cloudflare's Workers Logs.
- **Notification repair:** an outbox event that fails 10 times is parked as dead. `wire` is the operator's view (Cloudflare login, tenant and global D1). A tenant's `admin` has the same through its tenant Worker: `GET /api/admin/diagnostics` and `POST /api/admin/outbox/retry` (`{"ids": [...]}` or `{"dead": true}`). Retries republish collection revisions only; clients refetch through the collection rules. `POST /api/realtime/dispatch` flushes pending events without authority, like reconcile.
- **Retention:** delivery runs delete delivered events older than 7 days (500 per run); dead events stay until retried. Diagnostics never show record ids or fields.

### Encrypted tenant secrets

```sh
pnpm smoke:secrets      # local acceptance: checks, fresh local keys, health, the S-6-1-01 journey
pnpm journey:secrets    # the journey alone, against a running `pnpm dev:stack`
```

- **Storage:** each tenant Worker keeps secrets in its own `SECRETS` KV namespace as AES-256-GCM envelopes (`{v, alg, kv, n, c}`): a fresh 96-bit nonce per encryption, and additional authenticated data binding each ciphertext to its tenant, environment, key version, purpose and name. KV never holds plaintext or keys, and an envelope moved to another tenant, environment, version or name does not open.
- **Keys:** the data key is the Worker secret `DATA_KEY_V<n>` (32 random bytes, base64); the `DATA_KEY_VERSION` var names the active version. `takebase secrets init <tenant> [--env <name>]` generates it, or reads it with `--stdin` (for example `openssl rand -base64 32 | takebase secrets init tenant-a --stdin`). It is never an argument and never printed or logged. Init stores it first in the environment's untracked mode-600 keys file (`DATA_KEY_V1_TENANT_A`; `ops/.local.env` locally, the secrets file remotely), then installs it remotely through a temporary mode-600 file. It refuses when a key is already installed: it never replaces a key.
- **Escrow is your job:** keep a copy of the keys file outside this machine. Ciphertext alone cannot be recovered, and neither R2 backups nor Cloudflare can recover a lost key.
- **Check and status:** `takebase secrets check` asks each tenant's `/health/ready`, whose `secrets` check decrypts a random key-check canary (`unconfigured` until a key is installed, `error` when the key does not open KV). `takebase secrets status` shows key presence and the stored secrets' metadata, never a value.
- **API:** the secrets service is Worker-internal (`useContext().secrets`, `put`/`get`/`status`/`check`); no HTTP route accepts or returns a secret value. Locally, `takebase dev` hands each tenant Worker only its own key from a mode-600 file it removes on stop. Rotation and revocation come later.

### Backups

```sh
pnpm smoke:backups                 # local acceptance: checks, then the S-6-3-01 backup journey
takebase backup create --all       # or --tenant <id> | --global; [--env <name>]
takebase backup list               # newest first, each verified again now
takebase backup verify --latest    # or a backup id
```

- **What a backup holds:**
  - each selected D1 database as `wrangler d1 export` SQL, schema, data, indexes and triggers, with its `d1_migrations` history;
  - each tenant's `SECRETS` KV namespace as the stored AES-256-GCM envelopes and their metadata (ciphertext only);
  - `config.json`: the environment's tenant declarations, each Worker's binding names, the vars `TENANT_ID`, `TAKEBASE_ENV`, `DATA_KEY_VERSION` and `FIREBASE_DATABASE_NAMESPACE`, the repository's migration files with SHA-256, and the CLI version.
- **Where it goes:** one private R2 bucket per environment (`backupBucket` in `takebase.jsonc`), under `backups/<id>/` with a `manifest.json`. Locally it is a Wrangler-persisted bucket in `examples/workers/global/.wrangler/state-backups`. Remotely, `takebase backup init --env <name>` creates it inside the environment's name prefix, with no public access, no r2.dev URL and no presigned links. The CLI runs everything through your own Wrangler login, pinned to `CLOUDFLARE_ACCOUNT_ID`. Who can read backups is whoever can read that bucket in the Cloudflare account. No Worker has an R2 binding.
- **Manifest and verification:** the manifest lists every object with its size and SHA-256, each database's schema version (last applied migration) and migrations, each tenant's ciphertext count and the data key versions it needs, and a checksum of itself. Backups are found through `backups/catalog.json`, because Wrangler cannot list R2 objects. A backup is *verified* only when all of these hold, checked again on every `list` and `verify` (the result is never stored):
  - it is in the catalog;
  - its manifest and catalog checksums agree;
  - every object is present with the recorded size and hash;
  - every database export replays into an empty SQLite database that passes `integrity_check` and `foreign_key_check`, with the recorded migration history;
  - every KV line is a ciphertext envelope, with the recorded count and key versions.
  An interrupted backup never reaches the catalog. The checksums detect corruption, truncation, missing objects and edits, not someone with write access to the bucket who rewrites objects, manifest and catalog consistently.
- **Consistency limits:** each part is captured at its own time, recorded as `capturedAt`. A backup is **not** one atomic snapshot across the global database, the tenant databases and KV: a write that lands between two exports appears in one and not the other. Each D1 export is a single database's export by Wrangler. A running remote export blocks other requests to that database, and Cloudflare does not export databases with virtual tables. Size and timeout limits of large exports are not claimed here. D1 Time Travel is a separate Cloudflare feature these backups neither use nor replace. Locally, `backup create` refuses while the stack runs.
- **Not included:**
  - data keys, the keys and secrets files, passwords, API keys and account IDs. A restore needs the key versions the manifest lists, from the keys file or the escrow, so keep the escrow separately;
  - Firebase Auth users: export them with Firebase's own tools;
  - Realtime Database notifications, which are ephemeral triggers rebuilt from D1.
- **Restore order:** Wrangler exports tables in creation order. The global export lists `memberships` before the `tenants` table a later migration recreated, so a restore must defer or reorder foreign keys. Restore and prune are planned.

### Dev, build and deploy

```sh
node packages/cli/src/bin.ts dev [--fresh] [--seed '<command>']          # local stack; starts the emulators itself
node packages/cli/src/bin.ts build --env staging                       # bundle every Worker (--dry-run), build the app
node packages/cli/src/bin.ts deploy --env staging --plan               # read-only: what deploy would run
node packages/cli/src/bin.ts deploy --env staging --confirm staging    # deploy
```

`deploy` runs in a fixed order and stops at the first failure: global migrations, the global Worker and its `/health`, then each registered active tenant (migrations, Worker with its secrets, `/health`), then the app built with the environment's settings and its page. Every step can be run again. Before any change it refuses a Cloudflare login that cannot use `CLOUDFLARE_ACCOUNT_ID`, any Worker, D1 or Realtime Database name outside the prefix, and a tenant bound to another global Worker. `--plan` makes read-only calls only. Unprovisioned or disabled tenants are skipped; deploy never provisions. A local environment is never deployed.

### Collections and migrations

Run these from a Worker directory, or pass `--worker <dir>`; inside this repository `takebase` stands for `node <repo>/packages/cli/src/bin.ts` (from the root, `pnpm exec takebase` also works). Whether a command acts on the global or a tenant database is simply which Worker it targets; `--env` picks a Wrangler environment and `--database` a D1 binding when there is more than one.

```sh
cd examples/workers/tenant
takebase collection create claims --field title:text --field amount:integer?   # src/schema + src/collections, no rules yet
takebase collection inspect policies          # columns, rules, validation, filters, sorts and hooks
takebase migrate generate --name create_claims # drizzle-kit generate into the binding's migrations_dir
takebase migrate inspect --env tenant-a --sql  # applied/pending, history check, pending SQL
takebase migrate apply --env tenant-a          # wrangler d1 migrations apply --local, then re-check
```

A generated collection has no rules, so every operation is denied until you add them. Register it in `src/collections/index.ts` yourself.

`inspect` and `apply` stop with an error when the history does not match: an applied migration whose file is missing, SQL files and `meta/_journal.json` disagreeing, or a pending migration that sorts before an applied one. If a migration fails, Wrangler rolls it back and it stays pending; `apply` exits non-zero and never reports it as applied. Wrangler records migration names only, so editing an already-applied file cannot be detected: never do it.

Schema release policy:

- Migrations are append-only. Fix a mistake with a new migration; never edit, rename or delete an applied one.
- Review the generated SQL (`migrate inspect --sql`) before applying it anywhere, and commit it with the schema change.
- Only local databases are supported here. `--remote` is refused: applying to a remote database is a separately authorized release step, run tenant by tenant with `wrangler d1 migrations apply <binding> --remote --env <tenant>` after a backup. There is no automatic rollback.

Collections can declare Laravel-style model event hooks (`creating`, `updating`, `deleting` before the write; `created`, `updated`, `deleted` after it). Hooks run only after the collection's rule allowed the operation and the input validated; a before-hook's output is validated again, and side effects belong in the after-hooks, which run only once the write succeeded.
